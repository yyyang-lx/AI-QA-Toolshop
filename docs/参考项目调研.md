# Toolshop 测试项目参考项目调研

## 一、调研目的

为了提高 AI-QA-Toolshop 项目的完整性和实践价值，本次调研选择与 Web 电商系统测试、自动化测试相关的开源项目，了解其测试范围、技术选型和项目组织方式。

本项目以软件测试思维和质量保障过程为重点，自动化测试为辅助。因此，调研的主要目的是学习如何组织测试工作、设计测试场景、记录缺陷和补充自动化验证，而不是照搬大型自动化框架。

## 二、参考项目一：Practice Software Testing

### 2.1 项目地址

- 官方网站：https://practicesoftwaretesting.com/
- GitHub 仓库：https://github.com/testsmith-io/practice-software-testing
- With Bugs 版本：https://with-bugs.practicesoftwaretesting.com/

### 2.2 项目概况

Practice Software Testing 是用于软件测试练习的 Web 电商系统，提供商品浏览、搜索、分类、登录及购物车等业务功能。

项目还提供 With Bugs 版本，适合进行缺陷探索和测试练习。本项目选择该系统作为被测对象，可以围绕真实页面和业务操作开展功能测试，并在实际执行过程中记录观察结果。

### 2.3 值得借鉴的内容

1. **以业务流程组织测试：** 从商品浏览、搜索、商品详情到购物车，按照用户实际使用路径设计测试场景。
2. **关注异常和边界场景：** 除了验证正常操作，还应检查错误输入、重复操作、无结果场景和数据一致性。
3. **利用缺陷练习环境：** 通过 With Bugs 版本进行探索性测试，练习异常识别、复现和缺陷报告编写。
4. **区分预期结果与实际结果：** 不能仅凭页面显示异常就判断原因，应记录操作步骤、预期结果和实际结果。

### 2.4 对本项目的启发

本项目将继续使用官方在线演示环境，不自行部署被测系统。测试重点放在商品搜索、分类筛选、商品详情、购物车和登录等功能。

发现异常时，先保存证据并尝试复现，再判断是否形成正式缺陷记录。

## 三、参考项目二：Toolshop Test Automation Framework

### 3.1 项目地址

https://github.com/WolfGung/Toolshop-Test-Automation-Framework

### 3.2 项目概况

该项目是围绕 Toolshop 电商系统开展自动化测试的开源实践，可作为了解自动化测试项目组织方式的参考。

调研时应重点查看其 README、目录结构、测试脚本、依赖配置和测试执行方式，确认哪些设计适合初学者借鉴。

### 3.3 值得借鉴的内容

1. 自动化脚本应围绕明确的业务场景组织，而不是只堆积零散代码。
2. 测试脚本需要有清晰的断言，用于判断实际结果是否符合预期。
3. 项目应提供基本的运行说明，方便其他人理解环境要求和执行方法。
4. 自动化测试应与手工测试配合，不能只凭脚本运行成功就认定整个业务流程没有问题。

### 3.4 对本项目的启发

本项目不直接复制完整自动化框架，而是根据当前能力和 5 天周期，优先选择少量核心场景编写基础自动化脚本。

在实现过程中，重点理解测试数据、请求或页面操作、断言和结果记录之间的关系。若接口或环境条件不满足，则及时缩小自动化范围。

## 四、参考项目三：Toolshop Playwright Automation

### 4.1 项目地址

https://github.com/hasankanaran/toolshop-playwright-automation

### 4.2 项目概况

该项目提供基于 Playwright 的 Toolshop 自动化测试实践，可用于了解 Web 页面自动化测试的基本组织方式。

### 4.3 值得借鉴的内容

1. 将页面操作组织为清晰的测试步骤。
2. 使用断言验证页面元素、交互结果或业务状态。
3. 关注页面加载和交互时机，减少因等待不充分导致的不稳定失败。
4. 为测试项目提供清晰的安装和运行说明。

### 4.4 对本项目的启发

本项目已在 `automation/test_cart_ui.py` 中使用 Playwright 验证首页和购物车场景，保留小范围脚本，不引入复杂页面对象框架。当前执行仍依赖在线 With Bugs 环境；站点未响应和商品数据未就绪会单独标记，功能断言失败时保存截图。

## 五、参考项目对比

| 对比维度 | Practice Software Testing | Toolshop Test Automation Framework | Toolshop Playwright Automation |
|---|---|---|---|
| 主要用途 | 被测系统及缺陷练习 | 自动化测试实践 | Web 页面自动化实践 |
| 主要借鉴点 | 业务流程、风险和缺陷发现 | 测试组织、断言和运行说明 | 页面交互、等待与断言 |
| 对当前项目的作用 | 提供测试对象 | 提供自动化设计参考 | 提供页面交互与等待设计参考 |
| 当前采用方式 | 直接使用在线系统 | 参考设计，不整体复制 | 已用于少量购物车 UI 验证，不采用复杂框架 |

注：本表为初步调研和项目规划总结，不代表已经逐行分析或运行上述仓库中的全部代码。

## 六、对 AI-QA-Toolshop 项目的实施规划

结合项目周期和当前学习目标，确定以下实施策略：

### 6.1 测试分析与质量保障

- 编写测试方案和风险分析。
- 根据核心业务设计测试用例。
- 执行测试并保留真实结果。
- 对可复现的异常进行缺陷记录和分析。
- 编写测试总结，说明测试覆盖范围、发现的问题和遗留风险。

### 6.2 自动化测试

- 优先选择稳定、重复执行价值较高的场景。
- 使用 Python 和 pytest 练习测试脚本组织与断言。
- 根据实际接口能力决定是否使用 requests。
- 不为了使用更多技术而增加不必要的复杂度。

### 6.3 AI 辅助测试

- 使用 AI 辅助补充测试场景和异常输入。
- 人工检查生成内容是否符合业务逻辑。
- 对测试用例进行去重、修正和优先级排序。
- 记录 AI 建议、人工修改内容及实际验证结果。

## 七、调研结论

本次调研确定了项目的主要实践方向：

1. 以 Practice Software Testing 的 With Bugs 版本作为主要被测环境。
2. 以测试方案、风险分析、测试用例、执行记录和缺陷分析体现测试思维。
3. 参考现有开源项目的自动化组织方式，但不盲目复制大型框架。
4. 将 AI 用作测试分析辅助工具，并通过人工审核和实际执行保证结果可信。
5. 在 5 天项目周期内优先完成可验证、可解释、可展示的交付物。
